# Improve eforge PR title/body generation

## Problem / Motivation

eforge PR bodies for `landing.action: pr` currently render as noisy raw commit-log dumps in GitHub.

Evidence gathered:

- A screenshot shows GitHub rendering the PR conversation body as a long list of raw commit messages and trailers.
- `Models-Used:` and `Co-Authored-By: forged-by-eforge <noreply@eforge.build>` appear repeatedly.
- Direct PR creation currently delegates metadata generation to GitHub CLI via `gh pr create --base <base> --head <feature> --fill` in `packages/engine/src/worktree-ops.ts`.
- `WorktreeManager.issuePr` in `packages/engine/src/worktree-manager.ts` pushes the artifact branch, calls that helper, and falls back to `gh pr view` for existing PRs.
- eforge commit messages intentionally include `Models-Used:` trailers from `packages/engine/src/model-tracker.ts`.
- eforge commit messages intentionally include `Co-Authored-By:` attribution from `packages/engine/src/git.ts`.
- Those trailers are desirable in commits but undesirable as the primary PR body.
- Final landing already has access to `OrchestrationConfig`, `featureBranch`, `baseBranch`, and `ModelTracker` in `packages/engine/src/orchestrator/phases.ts`, which is enough to compose deterministic PR metadata.
- Stacked PR submission uses git-spice `branch submit --fill --no-web --no-prompt` in `packages/engine/src/stacking/git-spice.ts`.
- `packages/engine/src/stacking/landing.ts` discovers the PR URL after stacked PR submission.
- Stacked PRs likely have the same fill-from-commits problem, but exact git-spice title/body override support was not verified.
- `docs/roadmap.md` includes stacked PR polish and integration maturity.
- This bugfix fits the roadmap goals and does not introduce new roadmap scope.

Affected users:

- Anyone using eforge PR landing.
- Team workflows where PR descriptions are reviewed in GitHub.

Why it matters now:

- The screenshot demonstrates current PRs are noisy and unprofessional.
- Commit trailers should remain in commit history, but they should not dominate PR conversation content.

Observed reproduction:

1. Run an eforge build with PR landing enabled.
2. Let eforge create a GitHub PR.
3. Open the PR Conversation tab in GitHub.

Actual behavior:

- The PR body/comment contains raw commit subjects and trailers from multiple commits.
- `Models-Used:` appears repeatedly.
- `Co-Authored-By: forged-by-eforge <noreply@eforge.build>` appears repeatedly.

Expected behavior:

- The PR has an explicit reviewer-facing title and body generated by eforge.
- The body summarizes the build, plans, branch/base metadata, and models used without dumping raw commit trailers.

Local/static reproduction evidence:

- Direct PR creation uses `gh pr create --fill` in `packages/engine/src/worktree-ops.ts`, so PR metadata is inferred from commits.
- Stacked PR creation uses `git-spice branch submit --fill --no-web --no-prompt` in `packages/engine/src/stacking/git-spice.ts`, so stacked PR metadata is also likely inferred from commits.

Confirmed root cause for direct PRs:

- `packages/engine/src/worktree-ops.ts` creates direct PRs with `gh pr create --base <base> --head <feature> --fill`.
- `--fill` makes `gh` infer title/body from commit messages.
- eforge commits intentionally contain metadata trailers.
- `packages/engine/src/model-tracker.ts` appends `Models-Used: ...` when agents ran.
- `packages/engine/src/git.ts` appends `Co-Authored-By: forged-by-eforge <noreply@eforge.build>` to all engine commits.
- Multi-plan builds produce several plan/build/cleanup commits, so the inferred body becomes a raw commit-log dump with repeated trailers.

Likely root cause for stacked PRs:

- `packages/engine/src/stacking/git-spice.ts` submits stacked PRs with `git-spice branch submit --fill --no-web --no-prompt`.
- `packages/engine/src/stacking/landing.ts` discovers the PR URL after submit.
- PR URL discovery gives eforge an opportunity to post-process PR metadata if git-spice cannot set custom title/body during submit.

## Goal

Generate deterministic, reviewer-facing PR titles and bodies for direct and stacked eforge PR landings.

PR descriptions should summarize the build, plans, branch/base metadata, and models used without exposing raw repeated commit trailers, while preserving the existing commit trailer behavior in commit history.

## Approach

Add a shared PR metadata renderer, for example `packages/engine/src/pr-metadata.ts`, that returns deterministic `{ title, body }` from:

- `OrchestrationConfig`
- `featureBranch`
- `baseBranch`
- Optional `ModelTracker`

For direct PRs:

- Thread metadata through `executeLandingAction`.
- Thread metadata through `WorktreeManager.issuePr`.
- Thread metadata through `createPullRequest`.
- Replace `--fill` with explicit `--title` plus `--body-file`.

For existing direct PR fallback:

- Continue returning the existing PR URL.
- Optionally update the existing PR title/body with deterministic metadata so reruns repair stale/noisy descriptions.

For stacked PRs:

- Keep the git-spice submission flow for stack semantics.
- After PR URL discovery, call a shared `gh pr edit <url> --title <title> --body-file <tempfile>` helper.
- If editing fails after the PR was successfully created, treat the edit failure as non-fatal.
- If editing fails after the PR was successfully created, emit or record a diagnostic event or progress message.

Keep commit trailers unchanged:

- The bug is PR metadata generation, not commit attribution.
- `forgeCommit` should continue appending `Co-Authored-By: forged-by-eforge <noreply@eforge.build>`.
- Commit messages composed with a non-empty `ModelTracker` should continue including `Models-Used:`.

## Scope

In scope:

- Add a shared PR metadata renderer, for example `packages/engine/src/pr-metadata.ts`.
- Generate deterministic `{ title, body }` from `OrchestrationConfig`, `featureBranch`, `baseBranch`, and optional `ModelTracker`.
- Update direct PR creation to use explicit PR metadata instead of `gh pr create --fill`.
- Thread PR metadata through `executeLandingAction`, `WorktreeManager.issuePr`, and `createPullRequest`.
- Use explicit `--title` and `--body-file` for direct PR creation.
- Continue returning the existing PR URL when a direct PR already exists.
- Update existing direct PR title/body with deterministic metadata when the existing PR URL is found.
- Preserve stacked PR submission through git-spice.
- Post-process stacked PR metadata with `gh pr edit <url> --title <title> --body-file <tempfile>` after PR URL discovery.
- Treat stacked PR metadata edit failure as non-fatal when PR creation succeeded.
- Emit or record a diagnostic event or progress message when stacked PR metadata editing fails.
- Add unit or integration tests for direct PR creation arguments.
- Add unit or integration tests verifying direct PR body-file content excludes commit attribution trailers.
- Add unit or integration tests for existing direct PR fallback metadata editing.
- Add unit or integration tests for stacked PR landing metadata editing after PR URL discovery.
- Run `pnpm type-check`.
- Run `pnpm test`.

Out of scope:

- Changing commit attribution behavior.
- Removing `Co-Authored-By: forged-by-eforge <noreply@eforge.build>` from engine commits.
- Removing `Models-Used:` from commit messages composed with a non-empty `ModelTracker`.
- Replacing the existing git-spice stacked PR submit flow.
- Introducing new roadmap scope beyond stacked PR polish and integration maturity.
- Failing stacked PR landing solely because metadata editing failed after PR creation succeeded, under the current design assumption.

## Acceptance Criteria

- Direct PR creation invokes `gh pr create` with explicit `--title` and `--body-file` arguments instead of relying on `--fill` for the PR body.
- Direct PR bodies generated by eforge do not contain `Co-Authored-By:`.
- Direct PR bodies generated by eforge do not contain raw repeated `Models-Used:` trailer lines from individual commits.
- Direct PR bodies include the eforge plan set or PRD name when that information is available.
- Direct PR bodies include the base branch when that information is available.
- Direct PR bodies include the artifact branch when that information is available.
- Direct PR bodies include the plan list when that information is available.
- Direct PR bodies include a single reviewer-facing models-used summary when model usage information is available.
- Existing direct PR fallback still returns the existing PR URL when `gh pr create` reports an already-existing PR.
- Existing direct PR fallback updates the existing PR title/body with deterministic eforge metadata when the PR URL is found.
- Stacked PR landing preserves the existing git-spice submit flow.
- Stacked PR landing updates the discovered PR title/body with deterministic eforge metadata after a PR URL is available.
- Stacked PR landing remains successful when PR creation succeeds but metadata editing fails.
- Stacked PR landing emits or records a diagnostic describing the metadata edit failure when PR creation succeeds but metadata editing fails.
- Commit messages produced by `forgeCommit` continue to include the `Co-Authored-By: forged-by-eforge <noreply@eforge.build>` trailer.
- Commit messages composed with a non-empty `ModelTracker` continue to include the `Models-Used:` trailer.
- Unit or integration tests cover the direct `gh pr create` argument list.
- Unit or integration tests verify that direct `--body-file` content excludes commit attribution trailers.
- Unit or integration tests cover the existing direct PR fallback path.
- Unit or integration tests verify that metadata editing is attempted after the existing direct PR URL is found.
- Unit or integration tests cover stacked PR landing.
- Unit or integration tests verify that metadata editing is attempted after stacked PR URL discovery.
- `pnpm type-check` exits 0.
- `pnpm test` exits 0.
