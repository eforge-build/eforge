# Audit and Update Public Guide Sources

## Architecture Context

The public documentation site renders hand-authored guides from `web/content/docs/` and generated reference pages from `web/content/reference/`. Raw public Markdown mirrors under `web/public/docs/` are generated by `packages/docs-gen/src/generators/llms.ts`; do not hand-edit those mirrors in this plan. The current implementation, CLI/host surfaces, config schema, client route contracts, extension SDK, and input/scopes packages are the source of truth.

## Implementation

### Overview

Audit every editable public guide source under `web/content/docs/` from a user journey perspective, then make targeted updates for missing, stale, misleading, speculative, or confusing user-facing content. Keep changes concise and task-oriented. Update navigation, LLM manifest text, and documentation tests only when the audit changes the guide set, link targets, or enforced coverage snippets.

### Key Decisions

1. Treat `web/content/docs/` as the editable guide source and leave generated mirrors/reference artifacts to `plan-02-public-docs-regeneration`.
2. Use implementation files as source of truth rather than legacy root `docs/` content, except when legacy docs clarify repo conventions.
3. Prefer targeted edits inside existing guide pages over creating new pages, unless an entire user journey lacks a natural home.
4. Remove or rephrase speculative future/roadmap promises in public guides. Unsupported boundaries may be documented as current limitations without promising later behavior.

## Scope

### In Scope

- Audit and update public guide sources for these journeys: getting started, concepts, configuration, profiles, playbooks, extensions, CLI/API/reference entry points, integrations, stacking, recovery/troubleshooting, and glossary terminology.
- Compare guides against current user-facing behavior in:
  - `README.md` for the current public narrative only.
  - `package.json` and `web/package.json` for docs and web scripts.
  - `packages/eforge/src/cli/index.ts`, `packages/eforge/src/cli/playbook.ts`, `packages/eforge/src/cli/queue-control.ts`, `packages/eforge/src/cli/mcp-proxy.ts`, and related CLI modules for commands/options/tools.
  - `eforge-plugin/skills/` and `packages/pi-eforge/skills/` plus `packages/pi-eforge/extensions/eforge/` for Claude Code and Pi host behavior.
  - `packages/client/src/routes/`, `packages/client/src/api/`, and `packages/client/src/events/` for daemon API, route, SSE, event, queue, session-plan, recovery, model, and stack wire behavior.
  - `packages/engine/src/config.ts`, `packages/engine/src/schemas.ts`, `packages/engine/src/agents/`, `packages/engine/src/extensions/`, `packages/engine/src/queue/`, `packages/engine/src/recovery/`, and `packages/engine/src/stacking/` for config, pipeline, extension, queue, recovery, validation, and landing behavior.
  - `packages/input/src/` and `packages/scopes/src/` for playbook, session-plan, profile/playbook scope, and artifact protocols.
  - `packages/extension-sdk/src/` and `examples/extensions/` for public extension APIs and examples.
- Update `packages/docs-gen/src/manifest.ts` if guide descriptions or LLM entry points need new wording.
- Update docs/content tests when new coverage is added or stale coverage assertions need replacement.

### Out of Scope

- Do not edit generated artifacts under `web/public/`, `web/content/reference/`, `web/public/reference/`, `web/public/schemas/`, `web/public/llms.txt`, or `web/public/llms-full.txt` in this plan.
- Do not update legacy root `docs/` content except as a read-only reference for conventions.
- Do not add marketing copy, speculative roadmap claims, or internal implementation details that users cannot act on.
- Do not change runtime implementation code.

## Files

### Create

- None expected. If the audit proves a journey cannot fit any current page, create one new `web/content/docs/<slug>.md` page and update all navigation/generator/test files listed below.

### Modify

- `web/content/docs/getting-started.md` — verify install/init/first-build flow, daemon/Console wording, profile/landing flags, and remove dated or speculative billing claims.
- `web/content/docs/concepts.md` — verify pipeline, build source, session plan, provenance, queue, validation, profile, and stacked PR concepts against current implementation.
- `web/content/docs/configuration.md` — verify config tiers, profiles, toolbelts, playbook profiles, queue/auto-build, post-merge commands, landing/auto-merge, stacking, trunk sync, hooks, and extension settings.
- `web/content/docs/profiles.md` — verify profile scope precedence, active profile behavior, profile router precedence, harness options, and toolbelt fields.
- `web/content/docs/playbooks.md` — verify autonomous vs planning modes, scope tiers, frontmatter, `--after`, host commands, CLI limitations, and promote/demote behavior.
- `web/content/docs/extensions.md` — verify extension install/trust/loading/runtime support, contribution families, workstations, input sources, PRD enrichers, reviewer perspectives, validation providers, examples, and current unsupported boundaries.
- `web/content/docs/extensions-api.md` — verify SDK type/API reference prose, runtime support status, contribution contracts, storage helpers, policy gates, profile routers, input sources, validation providers, and unsupported boundaries.
- `web/content/docs/integrations.md` — verify Claude Code, Pi, standalone CLI, MCP/Pi tools, extension contributions, daemon HTTP API, hooks, input-source adapters, Langfuse, and Console dashboard coverage.
- `web/content/docs/stacking.md` — verify git-spice setup, `stack_id`/`stack_parent`, `--after` inference, workflow presets, sync, landing, conflict recovery, and auto-merge behavior.
- `web/content/docs/troubleshooting.md` — verify concrete remedies for daemon, docs drift, auto-build, queue controls, stack sync, recovery/resume, extension trust/policy, profile router, queue locks, and validation retries.
- `web/content/docs/glossary.md` — align terms with current docs and implementation names.
- `web/lib/nav.ts` — update only if a guide is added, removed, or retitled.
- `packages/docs-gen/src/manifest.ts` — update only if LLM guide descriptions or guide entry ordering need to reflect audited content.
- `web/__tests__/content.test.ts` — update coverage assertions for the public guide journey snippets and mirror/nav expectations.
- `test/reference-content.test.ts`, `test/extension-platform-docs-examples.test.ts`, `test/extension-tooling-wiring-runtime-docs.test.ts`, `test/profile-wiring-toolbelt-docs.test.ts`, `test/skills-docs-wiring.test.ts`, `test/stack-sync-surface-docs.test.ts` — update only when existing docs assertions reference stale snippets or new public-doc coverage needs a focused regression check.

## Verification

- [ ] Every Markdown source in `web/content/docs/` has title and description frontmatter, exactly one top-level `#` heading, and at least one `##` section.
- [ ] Each key journey has at least one task-oriented guide section with current commands, paths, or flags: getting started, core concepts, configuration/profiles, playbooks, extensions, integrations, CLI/API/reference, stacking, and troubleshooting.
- [ ] Public guide sources do not contain `Starting June 15, 2026`, `coming soon`, `TBD`, `TODO`, `future release`, `docs/config.md`, `docs/hooks.md`, or `docs/prd/`.
- [ ] Unsupported extension/workflow boundaries are phrased as current limitations, not promises of later features.
- [ ] Internal links in edited guide sources target existing `/docs/<slug>`, `/reference/<slug>`, `/schemas/<file>`, relative sibling pages, or external URLs.
- [ ] If a new guide page is added, `DOCS_NAV`, `packages/docs-gen/src/output-paths.ts`, `packages/docs-gen/src/generators/llms.ts`, `packages/docs-gen/src/manifest.ts`, `web/__tests__/content.test.ts`, and `web/public/docs/` generation coverage include the new slug.
