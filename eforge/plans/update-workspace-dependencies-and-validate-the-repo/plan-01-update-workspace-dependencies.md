# Update Workspace Dependencies and Validation Evidence

## Architecture Context

This repository is a pnpm workspace declared by `pnpm-workspace.yaml` with root `packageManager: pnpm@10.26.0`. Package manifests live at the root, under `packages/*`, and in `web/`. Workspace-internal dependencies use `workspace:*` specifiers and must remain workspace links. The root `package.json` also restricts dependency lifecycle build scripts through `pnpm.onlyBuiltDependencies`, currently `[
  "esbuild"
]`; do not expand this list unless a new build-script requirement is verified and documented in the evidence artifact.

Existing supply-chain evidence lives in `eforge/dependency-update-evidence.md`. Update that tracked file in the implementation diff with the new command results and review conclusions from this dependency update.

## Implementation

### Overview

Refresh dependency versions using pnpm-native workspace commands, regenerate `pnpm-lock.yaml`, inspect manifest and lockfile diffs, record supply-chain evidence, and make only dependency-compatibility code/config changes required for validation.

### Key Decisions

1. Use the package manager version declared in the root `package.json` and pnpm workspace commands (`pnpm outdated -r`, then usually `pnpm update -r --latest`) so manifest and lockfile changes follow the repo's package-manager convention.
2. Keep every `@eforge-build/*` internal dependency as `workspace:*`; dependency publication versions are out of scope.
3. Treat new, major-version, provider-SDK, toolchain, lifecycle-script, native/binary, or unfamiliar package changes as supply-chain-sensitive and capture the inspection results in `eforge/dependency-update-evidence.md`.
4. Keep compatibility fixes minimal: edit source/config only when `pnpm build`, `pnpm type-check`, `pnpm test`, `pnpm audit`, or the docs drift check exposes a dependency-related failure.

## Scope

### In Scope

- Inspect current workspace dependency state using pnpm commands.
- Update dependency ranges and lockfile resolutions across the workspace with pnpm.
- Preserve `workspace:*` specifiers for all internal `@eforge-build/*` package references.
- Preserve `packageManager: pnpm@10.26.0` and do not change the repo to another package manager.
- Update `eforge/dependency-update-evidence.md` with:
  - pnpm version and update command used.
  - `pnpm audit` command, exit status, and findings.
  - manifest diff-review conclusions.
  - lockfile diff-review conclusions.
  - `workspace:*` preservation findings.
  - unexpected new package assessment.
  - lifecycle-script inspection for newly introduced, major-version, or suspicious package changes.
  - repository inspection for newly introduced, major-version, or suspicious package changes.
  - maintainer inspection for newly introduced, major-version, or suspicious package changes.
  - native/build-behavior inspection for newly introduced, major-version, or suspicious package changes.
  - `npm diff` conclusions for risky or high-impact package changes, or an explicit statement that no package changes required `npm diff`.
  - validation command exit statuses.
- Apply targeted compatibility changes in code, TypeScript configs, build configs, or tests only when required by updated dependencies.

### Out of Scope

- Product behavior changes unrelated to dependency compatibility.
- Broad refactors.
- Package publish-version bumps.
- Changing away from pnpm.
- Expanding `pnpm.onlyBuiltDependencies` without verified package-script evidence and written justification in `eforge/dependency-update-evidence.md`.

## Files

### Create

- None expected.

### Modify

- `package.json` — update root dependency ranges and any pnpm overrides required by audit remediation; keep `packageManager` and workspace dev dependencies intact.
- `pnpm-lock.yaml` — regenerated by pnpm from updated manifests.
- `packages/*/package.json` — update workspace package dependency ranges produced by pnpm; keep internal `workspace:*` references unchanged.
- `web/package.json` — update web package dependency ranges produced by pnpm.
- `eforge/dependency-update-evidence.md` — replace stale dependency-update evidence with the current update command, audit results, diff-review conclusions, package inspections, `npm diff` conclusions, and validation results.
- Compatibility files as needed, limited to dependency-related failures. Likely areas include:
  - `packages/engine/src/harnesses/*.ts` for Anthropic or Pi SDK API changes.
  - `packages/eforge/src/cli/**/*.ts` and `packages/docs-gen/src/cli.ts` for Commander API/type changes.
  - `web/**`, `packages/console-ui/**`, and `packages/monitor-ui/**` for Next/Vite/React/Shiki/Vitest type or runtime changes.
  - `tsconfig*.json`, `vitest*.config.ts`, `web/next.config.mjs`, or build config files for TypeScript, Vitest, Next, Vite, tsup, or ESLint compatibility.

## Procedure

1. Baseline the workspace:
   - Confirm `pnpm --version` matches the root `packageManager` version or activate the declared version through Corepack without editing package-manager configuration.
   - Run `pnpm outdated -r` and use the output to identify direct updates, major-version changes, and high-impact packages.
   - Record the current `pnpm.onlyBuiltDependencies` value.
2. Update dependencies:
   - Prefer `pnpm update -r --latest` for a full workspace-aware refresh unless the baseline inspection gives a concrete reason to use a narrower pnpm-native command.
   - If audit remediation requires a pnpm override, add the smallest root `pnpm.overrides` entry that resolves the advisory and document it.
   - Run `pnpm install --frozen-lockfile` after updates to verify manifest/lockfile consistency.
3. Review manifests and lockfile:
   - Use `git diff -- package.json 'packages/*/package.json' web/package.json pnpm-lock.yaml`.
   - Verify all internal `@eforge-build/*` dependencies still use `workspace:*`.
   - Compare lockfile package entries before and after the update; list any newly introduced packages and decide whether they are expected transitives of updated dependencies.
4. Supply-chain inspections:
   - For every newly introduced, major-version, provider-SDK, toolchain, lifecycle-script, native/binary, or unfamiliar package change, inspect npm metadata. Useful commands include `npm view <name>@<version> repository maintainers scripts bin dependencies optionalDependencies dist --json` and `npm pack <name>@<version> --dry-run --json`.
   - Inspect lifecycle scripts, repository ownership, maintainer set, native/build behavior, package size/file count, and suspicious signs such as obfuscated scripts, unexpected network/download behavior, or new native binaries.
   - Run `npm diff --diff=<old-version> --diff=<new-version> <package-name>` for risky or high-impact changes. If no package qualifies, write that conclusion in the evidence artifact.
5. Validate and fix:
   - Run `pnpm audit` and record exact exit status/findings in `eforge/dependency-update-evidence.md`.
   - Run `pnpm build`, `pnpm type-check`, `pnpm test`, and `node packages/docs-gen/dist/cli.js check`.
   - For failures, make the smallest source/config/test changes tied to the dependency update, then rerun the failing command.
6. Final evidence pass:
   - Update `eforge/dependency-update-evidence.md` after the final diff is stable.
   - Ensure the evidence artifact names the update command, command exit statuses, package inspections, audit results, and diff-review conclusions from the final implementation diff.
