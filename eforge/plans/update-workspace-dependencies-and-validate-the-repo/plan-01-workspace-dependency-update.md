# Workspace Dependency Update and Validation Evidence

## Architecture Context

This repository is a pnpm monorepo. The root `package.json` declares `packageManager: pnpm@10.26.0`, `pnpm-workspace.yaml` includes `packages/*` and `web`, and CI installs with `pnpm install --frozen-lockfile` before running build, type-check, tests, and generated-doc checks. Internal packages use `workspace:*` specifiers and must remain workspace links.

The root `pnpm.onlyBuiltDependencies` list currently permits only `esbuild` build scripts. Dependency updates must not expand that list unless a newly introduced install/build script is reviewed, justified in the evidence artifact, and required for validation.

## Implementation

### Overview

Update external workspace dependencies with pnpm, keep workspace/internal dependencies intact, document the dependency-update review in a tracked evidence artifact, and apply only validation-driven compatibility fixes.

### Key Decisions

1. Use the repo's declared pnpm version and workspace-aware pnpm commands rather than changing package managers or editing the lockfile by hand.
2. Prefer a single plan because the dependency update, supply-chain evidence, and compatibility fixes must be reviewed together against the same manifest and lockfile diff.
3. Add a tracked evidence artifact under `eforge/` so the audit result and manual supply-chain review live with project-team workflow artifacts without publishing user-facing docs.

## Scope

### In Scope

- Run a workspace-aware dependency update using pnpm.
- Update root/package workspace manifests and `pnpm-lock.yaml` consistently.
- Preserve every existing `workspace:*` dependency specifier.
- Add `eforge/dependency-update-evidence.md` with audit, manifest, lockfile, package-inspection, and `npm diff` review conclusions.
- Make minimal compatibility fixes required by `pnpm build`, `pnpm type-check`, `pnpm test`, or the docs-gen CI check.

### Out of Scope

- Product behavior changes unrelated to dependency compatibility.
- Broad refactors.
- npm package publish-version bumps.
- Changing `packageManager` away from pnpm.
- Expanding `pnpm.onlyBuiltDependencies` without evidence that the new lifecycle/build behavior is required and reviewed.

## Files

### Create

- `eforge/dependency-update-evidence.md` — tracked evidence for the dependency update. Include sections for:
  - update command(s) and pnpm version;
  - `pnpm audit` command, exit status, and findings;
  - manifest diff-review conclusions;
  - lockfile diff-review conclusions;
  - confirmation that `workspace:*` specifiers remain intact;
  - unexpected new packages assessment;
  - lifecycle-script inspection for newly introduced, major-version, or suspicious package changes;
  - repository inspection for newly introduced, major-version, or suspicious package changes;
  - maintainer inspection for newly introduced, major-version, or suspicious package changes;
  - native/build-behavior inspection for newly introduced, major-version, or suspicious package changes;
  - `npm diff` review conclusions for risky or high-impact package changes;
  - a statement that no package changes required `npm diff` if the update contains no risky or high-impact changes.

### Modify

- `package.json` — update external dependency ranges when the chosen pnpm update command changes them; keep `packageManager` and `pnpm.onlyBuiltDependencies` unless a reviewed install/build-script requirement is documented.
- `pnpm-lock.yaml` — regenerate via pnpm, not manual lockfile editing.
- `packages/*/package.json` — update external dependency ranges generated by pnpm; keep internal `@eforge-build/*` dependencies as `workspace:*`.
- `web/package.json` — update external dependency ranges generated by pnpm.
- Compatibility-fix files, only if validation fails because of updated dependency APIs. Likely impact areas include:
  - `packages/engine/src/harnesses/` for Anthropic/Pi SDK type or API changes;
  - `packages/*/tsup.config.ts` for tsup/Vite/TypeScript build changes;
  - `packages/console-ui/`, `packages/monitor-ui/`, and `web/` for React, Vite, Next, Radix, Shiki, or UI-library type changes;
  - tests under `test/`, `packages/*/src/__tests__/`, or `web/__tests__/` only when an updated dependency changes type/runtime expectations.

## Implementation Steps

1. Confirm the working tree is clean before starting.
2. Record the current package-manager context:
   - `pnpm --version`
   - root `packageManager`
   - `pnpm-workspace.yaml`
   - root `pnpm.onlyBuiltDependencies`
3. Inspect existing dependency state with `pnpm outdated -r` and the current `pnpm-lock.yaml` importer sections.
4. Run the workspace-aware update. Use `pnpm update -r --latest` when direct dependency ranges are being refreshed; use `pnpm update -r` only if the inspection shows a lockfile-only in-range refresh is the narrow update that satisfies the observed state. Do not hand-edit `pnpm-lock.yaml`.
5. If the latest version of a direct dependency cannot pass validation with minimal compatibility fixes, hold back only that dependency to the newest passing version and record the package, attempted version, selected version, failing command, and reason in `eforge/dependency-update-evidence.md`.
6. Run `pnpm install --frozen-lockfile` after the update to verify manifest/lockfile consistency.
7. Run `pnpm audit`; capture its exit code and findings in the evidence artifact. Do not hide non-zero audit results.
8. Review `git diff -- package.json 'packages/*/package.json' web/package.json pnpm-lock.yaml` and record manifest and lockfile conclusions in the evidence artifact.
9. Identify newly introduced packages and major-version changes (direct or transitive) from the lockfile/manifests. For each newly introduced, major-version, or suspicious package change, inspect and record:
   - `npm view <pkg>@<version> repository maintainers scripts bin dist.unpackedSize`
   - lifecycle scripts (`preinstall`, `install`, `postinstall`, `prepare`);
   - repository URL/ownership changes;
   - maintainer changes or unusual maintainer metadata;
   - native/build indicators such as `binding.gyp`, `.node` files, prebuild assets, `node-gyp`, `napi`, or binary downloads.
10. Run and summarize `npm diff --diff=<pkg>@<old> --diff=<pkg>@<new>` for risky or high-impact package changes, including major updates, toolchain packages, framework packages, provider SDKs, packages with lifecycle scripts, native packages, or suspicious metadata. If no changed package meets those triggers, state that no package changes required `npm diff`.
11. Run validation commands and make minimal compatibility fixes until they exit 0.
12. Re-run the validation commands after compatibility fixes.
